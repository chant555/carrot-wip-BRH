# Rebuild All 관련 이슈 간결 초안

공통 참고: C3x에서는 시험하지 않았지만, 수정 대상은 공통 빌드·캐시 처리와 기기용 입력 백엔드이므로 기종 고유 특성에 대한 의존은 비교적 적다고 판단합니다.

## 이슈 1. [C4] Rebuild All이 손상된 빌드와 캐시를 정리하지 못합니다

안녕하세요.

Rebuild All을 실행해도 실제 정리가 이루어지지 않아 손상된 솔버가 캐시에서 다시 생성되는 문제가 있었습니다. 재부팅 후 정리하도록 수정한 뒤 기기에서 복구를 확인하여 검토를 요청드립니다.

### 기기 / 환경

- comma 4이며, `626b887d` 기준의 정차 상태에서 시험했습니다.
- 재빌드 요청과 정리 실패 처리를 수정한 패치 A를 단독 적용했습니다.

### 증상

- 기존 분석에서는 `scons`가 실패해도 성공 응답이 반환됐습니다.
- 손상된 캐시에서 생성물이 다시 만들어지면 재부팅 후에도 두 솔버와 `plannerd`를 불러오지 못했습니다.

### 원인 분석

- 로그인 셸이 `PYTHONPATH`를 덮어써 빌드 명령이 실패하는 경로가 있었습니다.
- 기존 최상위 `scons -c`는 삭제 대상 없이 성공 종료하는 경우가 있었고, `/data/scons_cache`도 남았습니다.

### 수정과 결과

- 버튼은 요청 파일을 저장하고 재부팅하며, 다음 부팅에서 런처가 빌드 상태와 캐시를 정리하도록 바꿨습니다. 삭제 실패 시 요청을 보존하고 후속 빌드를 중단합니다.
- A 단독으로 0바이트 솔버와 오염 캐시를 재현한 뒤 웹 재빌드 요청으로 복구했습니다. 정상 기동까지 약 7분 5초였고 솔버 불러오기와 기기 점검 다섯 항목이 통과했습니다. 첫 클릭은 `GIT_BUSY`로 거절됐으며, 이후 접수된 요청에서 복구했습니다.
- 6999 복구 화면은 정상 상태의 웹 버튼과 실제 컴파일 실패 상태의 터미널 명령을 각각 확인했습니다. 터미널 명령은 `touch /data/rebuild_all.request && sync && sudo reboot`이며, 수정된 요청 처리 기능이 있는 런처에서 사용했습니다.

### 검토 요청

재부팅 후 정리하고 실패한 요청을 보존하는 방식을 반영할 수 있을지 검토 부탁드립니다. A 단독에는 캐시의 동시 실행 보호가 없어 별도 잠금 수정 B와 함께 검토가 필요합니다. 전원 차단 중 복구는 검증하지 않았습니다.

감사합니다.

## 이슈 2. [C4] 시동 실패 화면의 복구 버튼이 터치에 반응하지 않습니다

안녕하세요.

컴파일 실패 후 나타나는 본체 화면에서 ‘리빌드 · 재부팅’ 버튼을 눌러도 반응이 없었습니다. 입력 갱신을 추가한 뒤 버튼 판정과 실제 복구를 확인했습니다.

### 기기 / 환경

- comma 4이며, `626b887d` 기준의 시동 실패 화면에서 시험했습니다.
- 운용 브랜치 `carrot-wip-brh`의 `8399bb83`도 해당 화면 소스가 같았습니다.

### 증상

- 버튼을 눌러도 화면 변화와 재빌드 요청 파일 생성이 없었습니다.
- 비교 진단에서 입력 갱신을 끄면 누름 네 번의 좌표가 모두 `(0, 0)`으로 남았습니다.

### 원인 분석

- 화면은 누름을 입력 장치에서 읽고 좌표는 raylib에서 얻는데, 반복문에 `poll_input_events()`가 빠져 있었습니다.
- 기기용 `COMMA` 백엔드는 `EndDrawing`에서 입력을 갱신하지 않습니다. 명시적으로 갱신하자 좌표와 버튼 판정이 회복됐습니다.

### 수정과 결과

- 패치 D는 기기용 백엔드에서 입력을 갱신하고, 재부팅 후에도 터치 좌표와 요청 수락 기록을 확인할 수 있도록 했습니다.
- A+D+E 조합에서 실제 컴파일 실패를 만든 뒤 사용자가 짧게 한 번 눌러 복구했습니다. 좌표 `(143, 207)`, 요청 수락과 재부팅 직전 요청 파일 존재가 기록됐습니다.
- 캐시 파일 2,521개를 정리하고 약 6분 57초 뒤 정상 기동했습니다. 솔버 검증과 기기 점검 다섯 항목이 통과했습니다.
- 성공 좌표는 원래 버튼 영역 안이었습니다. E의 아래쪽 영역 확장과 작업 중 안내 효과는 별도 진단과 로컬 검증으로 구분합니다.

### 검토 요청

기기용 백엔드의 입력 갱신 누락 수정을 검토 부탁드립니다. 현재 조건은 비공개 이름인 `raylib._BACKEND`를 사용합니다. 원시 터치 장치의 열기 여부와 백엔드는 다른 상태이므로 `touch.fd` 조건으로 대체하지 않았습니다.

짧게 한 번 눌러 복구한 사례는 한 번이며, 이전 첫 무응답과 추가 접촉의 원인은 미확정입니다. 모든 짧은 터치의 성공률을 입증한 결과는 아닙니다.

감사합니다.

## 이슈 3. [C4] 남은 잠금 또는 접근할 수 없는 SCons 캐시로 빌드가 막힙니다

안녕하세요.

남은 `config.lock` 또는 일반 사용자가 접근할 수 없는 캐시 때문에 빌드가 막히는 문제를 확인했습니다. 다른 빌드가 사용 중인 캐시를 지우지 않도록 공통 잠금 안에서 복구하는 방식을 검토 부탁드립니다.

### 기기 / 환경

- comma 4이며, `626b887d`에 A+B+C를 적용한 정차 상태에서 시험했습니다.
- 실제 `/data/scons_cache`와 부팅 런처를 사용했습니다. 아래 결과는 B의 캐시 복구 경로에 관한 것입니다.

### 증상

- 남은 `config.lock`과 사용할 수 없는 캐시에서 `SConsLockFailure`가 발생할 수 있습니다.
- `root` 소유로 접근이 제한된 캐시는 재부팅만으로 권한 문제가 해소되지 않습니다.

### 원인 분석

- 잠금 파일의 잔존 여부와 캐시 접근 권한을 구분해야 합니다.
- 잠금이나 캐시를 무조건 삭제하면 다른 빌드와 충돌할 수 있으므로, 빌드와 복구가 같은 배타 잠금을 사용해야 합니다.

### 수정과 결과

- B는 캐시 밖에 공통 `flock` 잠금을 두고, 이를 확보한 상태에서만 남은 잠금이나 사용할 수 없는 캐시를 정리합니다. 빌드끼리는 잠금 해제를 기다립니다.
- 남은 `config.lock`을 넣고 재부팅하자 잠금만 없어졌으며, 캐시 표식과 기존 파일 345개의 내용은 보존됐습니다.
- `root:root`, 권한 `0700`인 캐시는 부팅 중 관리자 권한으로 정리된 뒤 일반 사용자가 사용할 수 있게 재생성됐습니다. 두 경우 모두 정상 기동했습니다.
- 남은 잠금 시험의 로그 점검에는 외부 연결 오류가 있었으며, 캐시 복구 결과와 구분해 기록했습니다.

### 검토 요청

빌드와 복구가 같은 잠금을 사용하는 방식, 부팅 중 잠금·권한 복구 범위를 검토 부탁드립니다. 현재 B는 A 위에 적용하는 구성입니다. C의 손상 솔버 자동 감지는 별도 기능이며, 위 결과를 C의 자동 복구 실기 검증으로 해석하지 않습니다.

감사합니다.
