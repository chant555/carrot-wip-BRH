## 증상과 영향

기존 기기 분석 기록에서는 웹 화면의 Rebuild All을 일곱 번 눌렀으나 모두 성공으로 기록되고 재부팅은 일어나지 않았습니다. 서버 로그에는 `No module named 'libjpeg'` 오류가 남았습니다. 손상된 생성물과 오염된 캐시를 수동으로 제거한 뒤 재부팅하여 복구했습니다.

이 기록은 복구 버튼의 결함을 설명합니다. 다른 사용자들의 `git pull` 이후 빌드 실패가 모두 같은 원인이라는 뜻은 아닙니다. 해당 사용자들의 실패 당시 커밋과 로그, 캐시 권한 및 잠금 상태는 별도로 확보해야 합니다.

## 기존 분석에서 확인한 결함

1. 로그인 셸이 `PYTHONPATH`를 덮어써 정리 명령이 의존성 가져오기 단계에서 실패합니다.
2. 일부 웹 경로는 비동기 명령의 결과를 확인하기 전에 성공을 반환합니다.
3. 최상위 `scons -c`가 종료코드 0으로 끝나면서 삭제 대상을 처리하지 않습니다. `CompilationDatabase`를 정리 실행 때 등록하지 않는 수정이 제안되어 있습니다.
4. 실제 캐시인 `/data/scons_cache`를 지우지 않거나 다른 경로를 지웁니다. 손상된 결과를 캐시에서 다시 가져오면 소스부터 재빌드하지 못합니다.

10-03의 비파괴 정리 시험에서는 `scons -c -n --minimal`의 삭제 대상이 0개였고, 대상을 명시했을 때는 373개였습니다. 이 수치는 해당 커밋과 기기의 기록입니다. [보존된 출력](../analysis/2026-10-03-upstream/scons-clean-dryrun.txt)을 참고합니다. 다른 커밋의 삭제 개수를 같은 조건의 비교 결과처럼 합치지 않습니다.

## 제안하는 복구 동작

버튼은 저장소 밖에 재빌드 요청을 저장하고 재부팅합니다. 다음 부팅의 런처가 Params 빌드 전에 요청을 처리합니다. 요청 저장 실패 시에는 재부팅하지 않습니다. 파이썬 기반 요청 경로는 표준 라이브러리만 사용하며, 별도 리커버리 경로는 셸 명령을 사용합니다.

정리 명령 `scons -c`가 실패하더라도 빌드 상태와 캐시 삭제를 시도합니다. 다만 “삭제를 시도했다”는 사실을 성공으로 간주하지 않습니다.

- `.sconsign.dblite`, `/data/scons_cache`, `prebuilt`의 삭제 명령 결과와 잔존 여부를 확인합니다. 끊어진 심볼릭 링크도 잔존 대상으로 확인합니다.
- 초기화에 실패하면 성공 플래그를 설정하지 않고 재빌드 요청을 보존합니다. 런처는 실패 화면을 표시하고 후속 빌드를 중단합니다.
- 초기화에 성공한 뒤 요청을 지웁니다. 요청 삭제에 실패해도 실패로 처리합니다. 로그에는 정리 성공과 전체 빌드 성공을 구분해 기록합니다.
- 일반 사용자 권한으로 캐시를 지우지 못하면(예: `sudo scons` 로 만들어진 `root` 소유 캐시) `sudo -n` 으로 한 번 더 지웁니다. 캐시는 버려도 되는 데이터입니다.
