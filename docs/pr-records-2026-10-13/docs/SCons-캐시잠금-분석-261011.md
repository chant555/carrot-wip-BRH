# SCons 캐시 잠금 오류 분석

- 작성일은 2026-10-11이며, 마지막 수정일은 2026-10-13입니다.
- 기존 재현 보고, 10-11 로컬 검증, `626b887d` 기준 10-13 기기 시험을 구분하여 기록합니다. 이슈와 PR(변경 사항 병합 요청)은 제출하지 않았습니다.
- 기존 분석의 전체 내용은 [수정 전 기록](../analysis/2026-10-11-rebuild-review/SCons-캐시잠금-분석-261011.md.before.txt)에 보존했습니다.

## 관찰한 증상

다른 사용자 기기의 빌드 실패 화면에는 다음 오류가 표시되었습니다.

```text
SConsLockFailure: Timeout waiting for lock on '/data/scons_cache/config'.
```

사진만으로 실패한 커밋은 특정하지 못했습니다. 기존 분석은 화면 구성과 소스 행 번호를 바탕으로 오래된 코드일 가능성을 제시했으나, 확정된 버전 정보는 아닙니다.

## 기존 재현 결과와 해석

기존 분석에서는 기기의 SCons `4.10.1`과 작은 재현용 빌드 설정으로 다음 결과를 기록했습니다. 아래 표는 당시 기록이며, 10-13에 별도로 수행한 최신 패치 시험은 뒤 절에 구분했습니다.

| 조건 | 기존에 기록한 결과입니다. |
|---|---|
| `config.lock`이 남아 있습니다. | 약 5초 뒤 잠금 오류와 종료코드 120이 발생했습니다. 잠금을 지운 뒤에는 빌드가 정상 동작했습니다. |
| 관리자 권한의 빌드가 캐시를 `root:root 700`으로 만들었습니다. | 일반 사용자는 잠금 파일을 만들지 못해 같은 오류가 발생했습니다. 잠금 파일 삭제도 권한 오류로 실패했습니다. |
| 빌드를 60가지 시점에 강제 종료했습니다. | 잠금 파일이 남은 경우는 없었습니다. 이 시험만으로 전원 차단이나 모든 중단 상황을 배제할 수는 없습니다. |
| `config` 파일만 지웠습니다. | SCons가 파일을 다시 만들어 빌드했습니다. |

기존 분석에 따르면 잠금 구현은 `FileExistsError`와 `PermissionError`를 같은 대기 경로로 처리합니다. 따라서 오류 문구만으로 두 원인을 구분할 수 없습니다. 실제 실행 중인 다른 빌드가 잠금을 보유한 경우도 구분해야 합니다.

**[10-11 정정] 재부팅으로 복구되었다는 사실만으로 남은 잠금 파일이 원인이었다고 확정하지 않습니다.** 일시적인 동시 실행이 종료된 경우도 가능합니다. 관리자 권한으로 만든 캐시가 원인이라는 재현 역시 다른 사용자가 실제로 그런 조작을 했다는 증거는 아닙니다.

## Git pull과의 관계

기존 분석에서는 웹의 `git_pull` 경로가 저장소 설정 확인과 커밋 반영을 수행하며, 직접 SCons를 호출하지 않는다고 기록했습니다. 런처와 웹 갱신 경로가 같은 저장소 잠금을 사용하는 것도 확인했다고 기록했습니다.

**[10-11 정정] 조사한 경로에서 직접 빌드를 실행하여 잠금 오류를 만드는 동작은 확인하지 못했다는 범위로 결론을 제한합니다.** 업데이트 전후의 코드·환경 변화나 다른 실행 경로까지 배제한 것은 아닙니다. “pull 이후 빌드 실패”라는 관찰과 “pull이 잠금 오류를 만들었다”는 원인 주장을 구분해야 합니다.

다른 사용자의 원인 분류에는 실패 당시 커밋, 오류 전체 출력, 캐시와 잠금 파일의 소유권·권한, 동시에 실행한 빌드의 유무, 재부팅 전후 변화가 필요합니다. 조사한 기기의 정상 상태를 다른 사용자 기기의 실패 상태에 그대로 적용하지 않습니다.

## 함께 발견한 캐시 정리 문제

기존 `build.py`의 용량 제한 처리는 캐시 안의 모든 파일을 수정 시각 순으로 정리합니다. 따라서 오래된 `config`, `CACHEDIR.TAG`, `carrot_params_keys.sha256`도 삭제 대상이 됩니다. Params 스탬프 삭제는 다음 부팅에서 불필요한 재빌드를 유발할 수 있습니다.

통합 패치의 `prunable_cache_files()`는 정리 대상을 두 글자 이름의 하위 디렉터리 안에 있는 파일로 제한합니다. 현재 구현은 이름 길이를 확인하며, 16진수 문자만 허용하는 조건까지 구현한 것은 아닙니다. 이 변경은 잠금 자동 복구와 분리하여 검토할 수 있습니다.

## 10-11 동시 실행 검토 결과와 수정 (패치 B)

Codex 검토는 잠금 시간 초과, 캐시 소유권, 잠금 파일 존재만으로는 다른 빌드가 캐시를 쓰지 않는다고 증명할 수 없다고 지적했고, 공통 배타 잠금을 도입했습니다. 이 방향은 유지합니다. 다만 Codex 통합본은 그 잠금을 판정에 쓰지 않고 자동 복구를 모두 없애서, 상류에 있던 `config.lock` 자가 복구가 사라지고 `root` 소유 캐시는 그래픽 화면으로 복구할 수 없게 됐습니다. 또 잠금 파일을 쓰기 모드로 열어서, `sudo` 로 한 번 만들어지면 모든 빌드가 `PermissionError` 로 실패하는 새 고장이 생겼습니다(c4에서 재현). 분리본은 **잠금을 잡았을 때만 고친다**는 원칙으로 정리했습니다.

| 경로 | 동작입니다. |
|---|---|
| `agnos_init` | B에서 무조건적인 `config.lock` 삭제를 제거했습니다. A만 적용할 때에는 상류 동작을 유지합니다. |
| 잠금 파일 | `/data/scons_cache.build.lock`. 읽기 전용으로 열고 `flock` 합니다. 지우거나 바꾸지 않습니다. 심볼릭 링크와 일반 파일이 아닌 경로는 거부합니다. |
| `SConstruct` | 캐시 접근 전에 잠금을 잡고 프로세스가 끝날 때까지 유지합니다. 다른 빌드가 쓰고 있으면 최대 300초 기다리며, 대기를 시작할 때 이유를 한 번 출력합니다. |
| Params 빌드 | 생성물 제거부터 SCons, 검증, 스탬프 기록까지 잠금을 유지합니다(최대 300초 대기). 자식 SCons는 상속된 잠금을 검증해 재사용합니다. |
| `heal_scons_cache` | 요청 소비 전에 실행하고 잠금을 기다리지 않고 잡습니다. 잡으면 남은 `config.lock` 을 지우고, 쓸 수 없는 캐시는 지웁니다(`sudo -n` 대체). 잡지 못하면 건너뜁니다. 지워야 할 캐시를 지우지 못하면 시동 실패 화면을 띄웁니다. |
| Rebuild All·솔버 초기화 | 잠금을 잡은 경우에만 지웁니다. 사용 중이면 실패하고 요청을 보존합니다. |
| `build.py` 잠금 오류 | 캐시를 보존하고 재시도를 멈춥니다. 다음 부팅의 `heal_scons_cache` 가 고칩니다. |
| 캐시 크기 정리 | 잠금을 잡은 경우에만, 두 글자 버킷 디렉터리 안의 파일만 정리합니다. |

## 10-13 추가 검증: 운용 캐시의 실제 부팅 복구

| 실제 부팅 조건 | 관측 결과입니다. |
|---|---|
